# 青鸾考勤开发方案补充

本方案根据当前确认结果收敛第一阶段范围，后续以实际验证结果迭代。

## 一、第一阶段边界

- 当前只实现“对象存储模式”，暂不实现自建后端模式；后者作为未来独立部署模式保留协议边界。
- 对象存储适配器统一抽象为 S3 兼容接口，目标兼容阿里云 OSS、腾讯云 COS、标准 S3 以及自建 S3 兼容服务。
- Android 是主开发平台；Windows 同时建立工程和协议骨架，暂不追求功能对齐。
- Flutter Android 与 Electron Windows 共享数据格式、manifest、冲突决议格式和更新描述，不共享 UI。

## 二、身份、权限与密钥

- 不设计多账户登录和在线账号体系。
- 顶级管理员分发对象存储 `accessKeyId/secretAccessKey`（不同厂商可映射为 SecretId/SecretKey）。应用仅在本地安全存储中保存密钥，绝不写入 SQLite 业务快照、manifest、日志或仓库。
- 每个使用者首次填写本地显示名，并生成稳定的本地 `deviceId`；写入记录包含 `authorName`、`deviceId`、`updatedAt` 和操作类型。
- 所有用户共享同一对象存储空间，下载他人修改时必须在差异视图和审计记录中显示作者名。
- “管理员”是密钥分发和存储空间管理角色，不等同于应用内在线账户角色。后续如果需要撤销设备，应通过更换密钥或对象存储权限完成。

## 三、时间规则

- 业务工作日和同步 manifest 统一使用东八区（Asia/Shanghai）。
- 优先请求可信互联网北京时间服务；请求失败时使用设备本地时间，并记录 `clockSource=localFallback`，避免静默产生不可解释的日期差异。
- 数据库内部时间建议保存 UTC，同时保存计算出的 `businessDate`（东八区日期），防止跨午夜记录被错误分片。

## 四、同步与冲突处理

1. 先生成本地 manifest，与远端 manifest 按 `businessDate` 和 hash 比较。
2. 远端有、本地无：下载并校验 hash 后导入。
3. 双方 hash 相同：记录已同步，不产生冲突。
4. 双方 hash 不同：保留本地快照和远端快照，生成只读冲突会话。
5. 冲突界面支持字段级逐项选择（签到时间、签退时间、备注等），也提供“一键全部采用本地”“一键全部采用远端”“一键合并”快捷操作。
6. 合并完成后生成新的分片文件、manifest 和审计记录，再通过临时对象 + hash 校验 + 原子提交上传。
7. 删除必须记录 tombstone，否则另一端可能重新拉回已删除记录。
8. 所有同步操作必须可重试且幂等；网络错误、鉴权过期、hash 校验失败分别记录。

## 五、更新服务

保留三类更新源：GitHub Release、Gitee Release、自建更新服务。参考 AiChatApp 的做法：每个源可单独配置，比较 release tag 与本地版本，用户确认后下载；国内默认优先 Gitee，GitHub 作为备用，自建服务作为可配置源。下载后必须校验 checksum 或签名，再交给平台安装流程。

## 六、建议的目录和里程碑

- M0：工程骨架、数据模型、SQLite 迁移机制、密钥安全存储、东八区时钟、日志和错误模型。
- M1：单端考勤录入、查询、按日分片和 Excel 导出。
- M2：OSS/COS/S3 适配器、manifest 比对、断点/重试。
- M3：冲突快照、字段级审查、一键合并、审计记录。
- M4：GitHub/Gitee/自建更新源、Windows 客户端功能补齐。

## 七、仍需确认的非阻塞细节

1. Excel 导出固定列和是否需要打印模板。
2. “一键合并”默认策略：本地优先、远端优先，还是按字段更新时间优先。
3. 北京时间服务的首选地址；可以先实现可配置 HTTP 时间源并提供本地回退。

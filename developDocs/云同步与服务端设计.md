# 云同步与服务端设计

本文件定义「对象存储即后端」的协议与目录结构，供 Android 客户端与未来的自建服务端共同遵守。
当前 Android 版本已实现通知通道的拉取、版本比对、markdown 渲染与发布队列；数据文件的上传下载适配器、
签名上传与账号注册管理仍在后续里程碑。

## 一、总体思路

- 一个存储桶就是「一个组织的工作区」。所有客户端使用同一份桶内数据，远端不存在额外的业务 API。
- 客户端只在启动/回到前台时读取一个极小的清单 `index.json`，据此判断是否需要下载通知正文与数据文件。
- 数据以「按业务日 / 按月分片的小 JSON 文件」保存，天然支持增量同步、冲突字段级合并与删除墓碑。
- 自建服务端未来只新增两件事：**账号注册与管理**（谁可以拿到哪把密钥、属于哪个桶）以及**可选的写入代理**
  （让客户端不必在设备上持有写权限密钥）。文件同步路径与客户端协议保持不变。

## 二、桶内目录结构

```
/
├── index.json                      清单：数据 hash + 两个通知通道的版本
├── note.md                         管理员通知正文（Markdown）
├── dev-note.md                     开发者通知正文（Markdown）
└── data/
    ├── people.json                 人员名单（稳定 UUID + 停用/删除墓碑）
    ├── records/
    │   ├── 2026-10-16.json         每个业务日一个文件
    │   └── 2026-10-17.json
    ├── leaves/
    │   ├── 2026-09.json            请假记录按月分片
    │   └── 2026-10.json
    └── archive/                    可选：已关闭月份的冷数据，命名自由
        └── 2026-08/…
```

约定：

- 所有路径均为桶根相对路径，HTTPS 直链由客户端用「存储桶直链 / Endpoint + Bucket」拼接。
- 业务日一律使用东八区日期，文件名使用 `YYYY-MM-DD`；按月分片使用 `YYYY-MM`。
- JSON 统一 UTF-8、无 BOM、字段顺序不保证；任何校验以 `index.json` 里的 hash 为准。
- 通知正文固定放在根目录，由开发者/管理员手工或客户端上传，不使用 `data/` 前缀。

## 三、`index.json` 协议

```json
{
  "schema": 1,
  "generatedAt": "2026-10-17T09:12:04+08:00",
  "data": {
    "hash": "3f6a1c9e5b2d7f40c1a8...",
    "updatedAt": "2026-10-17T09:11:58+08:00",
    "files": {
      "data/people.json": "8a1c...",
      "data/records/2026-10-17.json": "2b7d...",
      "data/leaves/2026-10.json": "f30e..."
    }
  },
  "adminNote": {
    "version": "2026-10-17T09:12:04.221+08:00",
    "path": "note.md",
    "hash": "9c4e...",
    "title": "10 月 17 日考勤情况",
    "updatedAt": "2026-10-17 09:12"
  },
  "devNote": {
    "version": "1.0.2",
    "path": "dev-note.md",
    "hash": "77aa...",
    "title": "1.0.2 更新说明",
    "updatedAt": "2026-10-15 18:00"
  }
}
```

字段说明：

| 字段 | 含义 |
| --- | --- |
| `schema` | 协议版本，客户端忽略未知字段，遇更高版本只读取已知字段 |
| `data.hash` | 整个数据集的指纹（类似 commit hash），与本地不同即视为云端有新数据 |
| `data.files` | 逐文件 hash，用于只下载变化的日分片 |
| `adminNote` / `devNote` | 两个通知通道；`version` 单调递增（时间戳或语义版本），与本地已读版本不同才下载正文 |
| `note.path` | 正文对象键，默认 `note.md` / `dev-note.md`，允许自定义 |

解析容错：客户端同时接受 `adminNote` / `admin` / `note` 与 `devNote` / `dev` / `developerNote` 三种写法，
`version` 缺失时依次回退到 `hash`、`updatedAt`（见 `lib/core/reminders/notice_service.dart`）。

## 四、通知机制

1. 应用冷启动后请求一次 `index.json`。
2. 比较 `adminNote.version` 与本地已展示版本：
   - 相同：不下载正文，不打扰用户。
   - 不同：下载 `adminNote.path`（默认 `note.md`），渲染后写入本地已读版本。
3. `devNote` 使用完全相同的机制，只是对象键为 `dev-note.md`，用于开发者公告/版本更新说明。
4. 正文在底部面板渲染，支持标题、列表、引用、加粗斜体、行内代码、代码块、链接与分隔线（`MarkdownView`）。
5. 发送失败（桶未公开只读、未上传、网络错误）时保留本地旧状态，只在「通知中心 / 设置」里显示最近检查结果，
   不弹错误对话框，避免离线用户被打扰。
6. 管理员通知由应用内「首页 → 管理员通知」生成：写入本地待上传队列，内容包含发布人、东八区时间与
   正文；签名上传接入后写入 `note.md` 并更新 `index.json` 的 `adminNote.version`。

请求预算（客户端已实现）：

- 冷启动：1 次 `index.json`；无变化时不再发请求。
- 从后台回到前台：仅当离开前台超过 **1 小时**才再同步一次，避免频繁唤醒浪费请求次数。
- 设置里可关闭「自动检查」（`settings.autoSync = false`），此时只保留手动检查。

## 五、数据文件

### 人员名单 `data/people.json`

```json
{
  "schema": 1,
  "updatedAt": "2026-10-17T01:00:00Z",
  "people": [
    {"id": "uuid", "name": "林晓", "gender": "", "employeeId": "",
     "active": true, "deleted": false}
  ]
}
```

停用与删除都以 `active=false` / `deleted=true` 保留，历史考勤仍可显示姓名。

### 某日考勤 `data/records/YYYY-MM-DD.json`

```json
{
  "schema": 1,
  "day": "2026-10-17",
  "updatedAt": "2026-10-17T01:00:00Z",
  "entries": [
    {"id": "uuid", "personId": "uuid", "day": "2026-10-17",
     "fields": {"in": "09:00", "out": "18:00", "status": "正常", "note": ""},
     "fieldTimes": {"in": "2026-10-17T01:00:00Z"},
     "author": "主管", "updatedAt": "2026-10-17T01:00:00Z",
     "history": ["…"], "deleted": false}
  ]
}
```

- 每人每天一条记录，重复登记保持同一 `id`。
- `fieldTimes` 是字段级合并依据：冲突时按字段时间较新的一侧取值，时间相同或缺失保留本地。
- 删除使用墓碑（`deleted=true`），否则另一端会把已删记录重新拉回。

### 请假 `data/leaves/YYYY-MM.json`

```json
{
  "schema": 1,
  "month": "2026-10",
  "leaves": [
    {"id": "uuid", "personId": "uuid",
     "startDay": "2026-10-16", "endDay": "2026-10-18",
     "type": "事假", "status": "已确认", "reason": "",
     "author": "主管", "updatedAt": "2026-10-15T08:00:00Z",
     "history": ["…"], "deleted": false}
  ]
}
```

- `status` 取 `已确认 / 待确认 / 已取消`；只有 `已确认` 会阻止当天考勤登记。
- 区间跨月时，同一条请假在两边的月份分片里都会出现（按 id 去重合并）。

## 六、并发与冲突

1. 上传前重新读取 `index.json`，若 `data.hash` 已变化，先下载再合并，避免覆盖他人提交。
2. 合并按字段进行，冲突会话保留双方原值与作者，合并结果写回本地并进入待上传队列。
3. 上传使用「临时对象 + hash 校验 + 原子提交」：先 `PUT data/.tmp/<uuid>.json`，校验通过后再写最终键，
   最后更新 `index.json`。失败时清理临时对象，保证对端永远看不到半成品。
4. 所有操作幂等：同一 hash 重复上传不改变结果。

## 七、自建服务端（后续里程碑）

目标不是重写同步协议，而是把「分发密钥」和「管理账号」从人工变成系统：

- **组织 / 工作区**：一个组织绑定一个桶（或一个前缀），拥有唯一 `index.json`。
- **账号**：`id / 显示名 / 设备列表 / 角色（管理员 | 成员）/ 状态`；登录后由服务端签发短期令牌。
- **密钥管理**：默认仍可沿用「直接下发对象存储密钥」的方式；更安全的模式是由服务端签发**预签名 URL**
  或提供 **S3 兼容写入代理**，客户端不再持有长期密钥。
- **角色**：
  - 管理员：发布 `note.md`、维护人员名单与请假、导出数据、发放设备令牌。
  - 成员：登记自己的考勤、查看通知、提交请假申请（写入 `待确认`）。
- **审计**：记录谁在什么时间修改了哪个文件、对应 `index.json` 的哪次 hash。
- **保留的接口边界**：客户端已经把远端抽象为可替换的读写实现（对象存储 / 代理 / 服务端 API），
  账号体系接入后只需替换「取到 URL 与鉴权头」的一层。

最小的注册/管理接口草案（尚未实现）：

```
POST /v1/orgs                     创建组织（返回桶与工作区 id）
POST /v1/orgs/{id}/devices        注册设备，返回 deviceId 与令牌
GET  /v1/me                       当前身份、角色、组织
POST /v1/orgs/{id}/invite         邀请成员（下发只读/读写凭据）
POST /v1/orgs/{id}/rotate-secret  轮换密钥并作废旧设备
```

## 写通同步（保存即上传）

本地保存与云端上传合并为一个动作，避免「改完还要再去点同步」。

1. 业务方法把变更写入 `pendingDays` 后调用 `Workspace.persist()`；持久化完成后通知监听者。
2. `SyncService` 监听工作区，700 ms 去抖后执行一次上传：`data/workspace.json` → `note.md`（有待发通知时）→ `index.json`。
3. 快照 payload 剔除 `pendingDays`：待上传队列是设备本地状态，放进快照会让上传后的 hash 漂移，导致每次刷新都误判为「远端有新版本」。
4. 成功后清空 `pendingDays`、写入 `lastSync`，状态置为「已自动同步」；失败保留队列、状态置红，但不自动重试——由下次保存、启动、回前台、手动同步或记录页下拉触发，避免坏密钥打成请求死循环。
5. 拉取路径（记录页下拉 / 同步中心「立即同步」）：先推本地变更，再取 `index.json` 的 `data.hash` 与本地快照 hash 比对；一致提示「已是最新」；本地队列为空时下载 `data/workspace.json` 覆盖本地，队列非空则只提示不覆盖。
6. 设置项 `autoUpload`（默认开）可关闭自动上传，关闭后仅保留手动同步。
### 快照内容与 hash 稳定性

云端快照只包含业务数据：`people`、`entries`、`leaves`，以及 `notices` 里以 `note` 开头的发布元数据（`noteVersion`、`noteTitle`、`noteBody` 等）。

以下字段属于设备本地状态，既不上传也不参与 hash：`identity`、`deviceId`、`settings`、`pendingDays`、`lastSync`、`notices.lastResult` 等检查结果。早期版本把这些字段一起上传，导致每次启动后的通知检查都会改写本地 payload，刷新时被误判为「云端有新版本」并回灌旧数据；现在改为投影响应只剩业务字段。

`refresh()` 还会做一次自愈：当清单 hash 与本地不一致时，先取回远端快照并按同样规则投影比较，内容一致就只重写清单与快照（修好 hash），不再用旧数据覆盖本地。
